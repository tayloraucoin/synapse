# How should Synapse read (never write) events from several Google accounts and calendars, as a grant separate from Supabase sign-in, without hitting consent-screen, verification or quota problems?

## Answer

Create a dedicated OAuth "Web application" client for the Calendar connection, preferably in its own Google Cloud project. Request only `https://www.googleapis.com/auth/calendar.readonly` ("See and download any calendar you can access").\[26\] The narrower option is the pair `calendar.calendarlist.readonly` + `calendar.events.readonly`.\[27\] Send users to `https://accounts.google.com/o/oauth2/v2/auth` with `access_type=offline`, `prompt=consent select_account` and a `state` value.\[28\] Optionally add `login_hint`.\[28\] A refresh token comes back on the code exchange at `https://oauth2.googleapis.com/token`. Revoke with `https://oauth2.googleapis.com/revoke`. \[28\]\[29\] Google allows 100 refresh tokens per Google Account per client ID; the oldest is silently invalidated when that is exceeded. Refresh tokens also stop working after six months unused.\[30\] Do not run the connection in "Testing": test users' authorizations expire seven days after consent, refresh tokens included. Publish the app "In production".\[31\] Google's help center says personal-use apps with fewer than 100 users need not be verified. Those users click through the "unverified app" screen, and the project has a lifetime cap of 100 new users.\[31\]\[32\] List calendars with `calendarList.list`. Read a week with `events.list` (`timeMin`, `timeMax`, `singleEvents=true`, `orderBy=startTime`, page size up to 2,500, default 250).\[33\] Map `attendees[self=true].responseStatus`: `accepted`, `tentative`, `needsAction`, `declined`.\[34\] Quotas since May 1, 2026 are 10,000 requests/minute/project, 600/minute/user/project and a 1,000,000/day/project billing threshold.\[35\] Synapse's polling uses well under 1% of these.

## Synthesizer's notes

- Separate Cloud project: G1.9 says revocation clears all scopes granted "to a project" for all its clients. Putting the Calendar client in its own project keeps a Calendar disconnect from touching Supabase sign-in.
- Scope choice: `calendar.readonly` is one scope and is documented for both listing and events (G1.2, G1.3). The pair `calendar.calendarlist.readonly` + `calendar.events.readonly` is narrower, and Google's CalendarList: list reference documents `calendar.calendarlist.readonly` as enough for listing (G1.3). Either satisfies C-USE-settings-connecting-2.
- Mapping status to the UI (judgment): with no `attendees` array, or with `organizer.self = true`, treat the event as accepted (solid band). With `attendees[self].responseStatus` of `accepted`, show solid. With `tentative` or `needsAction`, show dashed with "Add to day". With `declined`, hide. Hide event `status = cancelled`. Consider excluding `workingLocation` and `birthday` through `eventTypes`.
- Snapshots are per week (`google_event_snapshots`), so use full `events.list` with `timeMin`/`timeMax` rather than syncToken (G3.11). The quota headroom (G4.7) makes this cheap.
- Treat `invalid_grant` on refresh as "Reconnect". Causes include Testing-mode expiry, six months unused, user revocation and the 100-token rotation (G1.7, G2.2).\[48\]\[49\]
- With fewer than 100 users the app can stay unverified (G2.7). Friends will see the "unverified app" click-through, and every new user counts against the lifetime cap of 100 (G2.6).\[31\] If that becomes a problem, sensitive-scope verification is the route.

## What this means for the build

1. Create a separate Google Cloud project with a "Web application" OAuth client for Calendar, distinct from Supabase's sign-in client. Register the Synapse callback as the exact redirect URI. (G1.4, G1.9, G1.12)
2. Configure Data Access with only `calendar.readonly`, or the narrower pair `calendar.calendarlist.readonly` + `calendar.events.readonly`. Google documents the narrower pair for `calendarList.list` and `events.list`. Record the console's sensitive/non-sensitive label in the ticket. (G1.1-G1.3, G2.8)
3. Set publishing status to "In production" and do not ship in Testing. Accept the unverified-app screen under the personal-use exception. Add a support note about the lifetime cap of 100 users. (G2.1, G2.2, G2.5-G2.7)
4. Connect URL: `access_type=offline`, `prompt=consent select_account`, `state`, optional `login_hint`, no `include_granted_scopes`. Add `openid email` to identify the account. (G1.4-G1.6, G1.13, G2.4)
5. Token store: encrypted refresh token per `google_accounts` row, plus `refresh_token_expires_in` if returned. On `invalid_grant`, show "Reconnect". Disconnect calls `https://oauth2.googleapis.com/revoke` and deletes the token. (G1.7, G1.8, G1.10, G1.11)
6. Calendars sync: `calendarList.list`; store `id`, `summaryOverride ?? summary`, `backgroundColor`, `primary`, `accessRole`, `hidden`, `deleted`; default `enabled` from `selected`. (G3.1)
7. Week read per enabled calendar: `events.list` with `timeMin`/`timeMax` for the week, `singleEvents=true`, `orderBy=startTime`, `maxResults=2500`, `maxAttendees=1`, `timeZone`; follow `nextPageToken`. (G3.2, G3.7)
8. Event mapping: self `responseStatus` gives solid, dashed or hidden; no-attendee and organizer events are solid; `start.date` means all-day; `eventType` filter. (G3.4-G3.9; mapping is judgment)
9. Error handling: truncated exponential backoff on 403/429 (maximum 32-64 seconds). (G4.4, G4.5)
10. Cadence: reuse the Linear schedule; budget about 15 requests per user per sync. No push notifications in this epic. (G4.2, G4.3, G4.6, G4.7)
