# How should Synapse connect to Linear (OAuth, several workspaces, read assigned issues, move issue state, stay within limits) for a single-user planner that polls instead of using webhooks?

## Answer

Register one OAuth2 application in Linear under Settings > Administration > API. That page needs workspace admin permission.\[1\] Linear recommends a dedicated workspace for managing the app.\[2\] Set the app's distribution to "public" so other workspaces can install it.\[3\] Send users to `https://linear.app/oauth/authorize` with `response_type=code`, `scope=read,write`, `actor=user` (the default: changes are attributed to the authorizing user), a `state` value, PKCE (`code_challenge_method=S256`), and `prompt=consent` when adding another workspace. Exchange the code at `POST https://api.linear.app/oauth/token`. The response contains a Bearer access token valid for 24 hours (`expires_in: 86399`) and a refresh token. Refreshing returns a new access token and a new refresh token. A 30-minute replay grace period covers lost responses. Revoke with `POST https://api.linear.app/oauth/revoke` (`token` field). Linear documents no scope narrower than `write` for changing issue state; `issues:create` and `comments:create` only create.\[2\] Fallback: a personal API key per workspace, sent as `Authorization: <API_KEY>` with no "Bearer". It can be restricted to Read/Write/Admin/Create issues/Create comments and to specific teams. Admins can turn off member API keys.\[1\]\[4\] Reads use `viewer.assignedIssues(filter: …)` with Relay pagination (`first`/`after`, default 50).\[5\]\[6\] Rate limits for OAuth apps are 5,000 requests and 2,000,000 complexity points per hour per user. No single query may exceed 10,000 complexity points. Exceeding a limit returns HTTP 400 with `extensions.code = "RATELIMITED"`.\[7\] Webhook creation requires a workspace admin or an OAuth token with `admin` scope, which confirms the spec's choice of polling.\[8\] Exact schema field types and the `issueUpdate` input could not be read from the schema in this pass and are marked [NOT VERIFIED] below.

## Synthesizer's notes

- The spec stores `token_expires_at` and a refresh token per connection; L1.13 to L1.15 make both necessary. Refresh is single-flight per connection: rotation means a stale refresh token fails. Persist the new pair atomically.\[15\] The 30-minute grace period (L1.15) is the recovery path if a write is lost.
- `client_id` in `linear_connections` is useful if the app is ever re-registered: L1.17 says secret rotation keeps tokens, but a new app would not.
- Treat "duplicate" (L3.6) as closed alongside completed/canceled until confirmed. The spec's "a sync that finds a placed issue closed closes the task" should use the closed-type set, not a single type.
- App webhooks (L6.2) may give push updates without an admin. This is worth a spike but not a dependency.
- Linear advises against polling (L5.7). The spec's cadence is still small: 13% of the hourly complexity budget at worst (L5.10).

## What this means for the build

1. Register one Linear OAuth app as "public", in a workspace where Taylor is admin. Redirect URI is the Synapse server callback. (L1.1, L1.2, L2.1)
2. Build the authorize URL with `response_type=code`, `scope=read,write`, `actor=user`, `state`, PKCE S256, and `prompt=consent` for "+ Add a workspace". (L1.3-L1.6, L1.11, L2.3)
3. Token store: access token, refresh token, `token_expires_at = now + expires_in` (about 24 hours), `scopes` as a string. Refresh on expiry or a 401 with single-flight and atomic swap. On refresh failure, show "Reconnect". (L1.12-L1.15)
4. Disconnect calls `POST /oauth/revoke` with `token`; treat 400 "already revoked" as success. (L1.16)
5. Identify the workspace after connect by querying `viewer` and its organization. A spike must confirm the field names `organization { id name urlKey logoUrl }`. (L2.5, L3.7)
6. Read query: `viewer.assignedIssues(first: 50, filter: { state: { type: { nin: [closed types] } } })` with explicit `first` on `children` and `labels`. Paginate with `after`. (L3.1-L3.3, L5.4, L5.8)
7. Done-state resolution: `workflowStates` filtered to team and `type: completed`, lowest `position`, cached per team in the snapshot. A team can have several completed states and has no default done state; a spike must confirm the filter fields. (L3.4, L3.5, L4.3, L4.4)
8. Outbox write uses `issueUpdate` with `stateId`, stored as `linear_prev_state_id` for reopen. A spike must confirm the mutation shape. (L4.1, L4.2)
9. Rate-limit handling: read `X-RateLimit-*` and `X-Complexity` headers. Treat HTTP 400 with `RATELIMITED` as back-off-until-reset. (L5.5, L5.6)
10. Keep the polling cadence as specified; the arithmetic shows wide headroom with explicit page sizes. (L5.10)
11. Fallback ticket (optional): a personal API key per workspace, sent as `Authorization: <key>`, restricted to Read+Write and specific teams. Show a clear message if the admin has turned off member keys. (L2.6-L2.8)
12. No webhook ticket. Webhooks need an admin. App webhooks are a later spike. (L6.1, L6.2)
