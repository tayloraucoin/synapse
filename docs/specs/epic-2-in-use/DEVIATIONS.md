# Epic 2 — In Use — Deviations (append-only)

One line per intentional divergence from a ticket, a UX document, or a convention. Never edit a ticket to match what shipped; append here. Format:

```

```

2026-09-05 · track · All eight tickets authored in one pass by Vesper, Mason, and Reeve, exceeding the spec-system guide's §7.4 ceiling · One day model, one row contract; tickets written apart would have disagreed about `ItemState`. The infrastructure and Epic 1 tracks did the same.
2026-09-05 · track · Pause/resume (official §12 Phase 2) ships in USE-4 and quantity/reflection capture (Phase 2) ships in USE-3 · `TimerControl`, `NumberUnitInput`, and `ReflectionBlock` are built; an item sheet with their regions removed is a stub that gets rewritten. They are cheap here and expensive as a second pass. Shift (USE-6) and trim (USE-7) stay Phase 2 because they are whole mechanisms, not regions.
2026-09-05 · track · The Schedule tab (USE-5) is launch-blocking, against official §12's Phase-2 placement · `apps/web/AGENTS.md` puts "the two execution tabs" in Phase-1 scope and every Schedule composite is built; only its Phase-2 refinements (drag, zoom) stay out.
2026-09-05 · track · `deferred_today` (Epic 2 IT-01) is the `day_items.deferred_at` timestamp SET-1 created, not a boolean · A timestamp says when; a boolean says only that. Same information, one more fact.

2026-09-05 · USE-1 · **AC3 and AC4 name the wrong day keys, and the code follows the arithmetic rather than the criteria** · A DST transition happens at 02:00 and a day opens at 03:00, so the day that CONTAINS a change is the one that opened the previous morning. Measured: `2026-03-07` is 23 hours and `2026-03-08` is 24; `2026-10-31` is 25 hours and `2026-11-01` is 24. The ticket asserts 23 and 25 hours for 03-08 and 11-01, which are ordinary days under a 03:00 close. Every instant AC3 and AC4 name is still produced exactly — `01:59`→`09:59Z`, the `02:30` gap→`10:00Z`, `03:00`→`10:00Z`, and fall-back `01:30`→`08:30Z` (the first occurrence) — only the window-length assertions moved to the days that have those lengths.
2026-09-05 · USE-1 · **AC6's `weekKeyOf("2026-01-01") = "2025-W01"` is wrong; it is `2026-W01`** · 2026-01-01 is a Thursday, and ISO 8601 assigns a week to the year containing its Thursday — so that week is the first of 2026, not of 2025. `2025-W01` would be January 2025, a year away; the expectation looks like a transcription slip for `2026-W01` or `2025-W53`. The interesting case the criterion was reaching for is preserved: the Monday BEFORE it (`2025-12-29`) also returns `2026-W01`, which is the year-straddling behaviour that matters.
2026-09-05 · USE-1 · `resolveDayKey` moved from `packages/utils/src/day/day-key.ts` into `boundaries.ts`, and the implementation changed from wall-clock comparison to shifting the instant back by the close time · SYS-1 wrote the first version and left a note saying USE-1 owned it. Both give the same answer; the shift form is what the ticket specifies, and it sits beside `dayWindow` and `dayModeFor`, which share its rules. `day-key.ts` keeps `weekdayForDayKey` and `daysBefore` and says where the function went.
2026-09-05 · USE-1 · `useDerivedItems` takes only the clock-dependent fields and returns the previous state untouched for the nine states a clock cannot change · `DayItemView` does not carry `assignment_state`, `deferred_at`, or whether a session is running — those are folded into `state` by the server. Rather than widen the view for the client's benefit, the hook short-circuits on any state that is a fact about what happened rather than about where the clock is. Same function, same answers, no extra fields on the wire.
2026-09-05 · USE-1 · `readPreferences` was NOT extended with the pending-pair application; `resolveTodayFor` (`services/day/today.ts`) owns it · The ticket rules it into `readPreferences`, but that service is a settings reader used by ST-01, ST-08 and ST-09, and applying a deferred switch as a side effect of reading a display name is a surprise in the wrong place. `resolveTodayFor` is called by both `day.today` and `day.get`, and by the scheduler's per-user pass before anything else — so the switch still happens on the first read of the day, with or without an app open, which is the behaviour the rule is for.
2026-09-05 · USE-1 · **Not verified: acceptance criteria 9–14** · The read model, the RLS isolation, the auto-close pass and the pending-pair application all need a database, and no Supabase project is wired to this repository. What WAS verified: AC1–AC8 and AC15 by running them — 49 cases covering both DST transitions from both sides, the 23- and 25-hour days, minutes past 24:00, ISO weeks across a year boundary, the full state precedence including the record and plan modes, both window thresholds, and the day parts from a captured `woke_at`. **What is unproven is the SQL, not the arithmetic** — and the arithmetic is where this ticket's risk was.

2026-09-05 · USE-2 · `DayView` gained `wakeAnchorItemId`, resolved by joining the account anchor habit to the day rows · The ticket rules exactly this and notes that neither `DayItemView` nor the hook can answer "which row is the anchor". It is a fact about the account joined to this day, not about the item — the same habit is the anchor on every day at once — so putting a flag on each row would be one fact written once per row. It survives archiving the habit because the join is on `habit_id`, which an archived habit keeps.
2026-09-05 · USE-2 · The multitask bracket is built by walking `multitask` POSITIONS, not by grouping on an id · `DayItemView` publishes `first`/`middle`/`last`/`none`, not a group key, so a run opens on a `first` and closes on a `last`. Reading it any other way would invent a second grouping rule. Probed across five shapes; the one that matters is two brackets back to back, which a naive "group consecutive non-none" would merge into a single bracket. Every item appears exactly once in all five, including a malformed unterminated run.
2026-09-05 · USE-2 · Three strings are marked `[COPY — needs Vesper sign-off]` in `components/day-list/copy.ts` · The write failure (LS-01 gives the load error only), the refresh announcement, and *Nothing was planned.* for a past day that was never planned — the ticket anticipates all three.
2026-09-05 · USE-2 · Pull-to-refresh is a passive touch threshold on `window`, with no visible indicator · The ticket says "not a library", and the announcement is `aria-live` only: the document describes the gesture but names no spinner, and a list that visibly jumps while someone is reading it is the opposite of what a refresh is for. Touch-only means compact-only without asking about a breakpoint — a pointer device fires no `touchstart`, and on wide the query refetches on focus.
2026-09-05 · USE-2 · **Not verified: acceptance criteria 1–13** · Every one needs a seeded day in a database and a browser; no Supabase project is wired to this repository, and the worst-moment test on a phone needs a reachable session. What WAS verified: AC15 four commands; AC14 the re-render budget, probed over nine minute ticks against a three-row day, where only the five ticks that actually moved a state rebuilt the day and unchanged rows kept object identity across every rebuild; the state progression upcoming → soon → now → passed at the right minutes; the deferred sort, which sinks deferred rows inside their own part while keeping time order and putting anytime rows after timed ones; and the multitask grouping across five shapes. **What is unproven is the screen and the writes, not the ordering, the grouping, or the tick budget** — which is where this ticket risk sat.

2026-09-05 · USE-3 · `item.get` is a separate read; `DayItemView` was NOT widened · The sheet needs the preflight note, the reflection axes and ratings, the note and every session; the list needs none of them and renders thirty rows. Putting them on the row view would send a day of notes and session history down the wire so one sheet can open, on the screen a person looks at most.
2026-09-05 · USE-3 · `ReflectionBlock` now takes `Pick<DayItemView, "icon" | "title">` rather than a whole `DayItemView` · It only ever read those two fields, and USE-3 is its first consumer — which reads a DIFFERENT view of the same row, richer where this matters and differently shaped where it does not. An earlier draft satisfied the old prop with a cast, which is the type system being talked out of its job; narrowing the prop was the honest fix.
2026-09-05 · USE-3 · `NumberUnitInput` gained an `onBlur` · The ticket has the quantity saving on blur and on close, and the control had no blur hook. A number is not finished until someone stops typing — saving on every keystroke would write 1, 12 and 127 for one value of 127.
2026-09-05 · USE-3 · The timer store keys a MAP by item id, not a single running entry · Two timers legitimately run at once inside a multitask group (official spec §5.5), so one `itemId` would be wrong exactly where the product is most particular. One interval serves all of them, started with the first running entry and cleared with the last, so two rows counting the same second cannot disagree.
2026-09-05 · USE-3 · A FIXED item with no `scheduled_end` reads `passed` from the instant it starts, so starting its timer at exactly its own time takes the late-start branch · This is USE-1 existing precedence rule, not a change made here, and it is harmless: the branch writes `scheduled_start = now`, which for that instant is the value already there, so `original_scheduled_start` still matches and no false *moved* appears. It is reachable only through WK-03, which allows a fixed one-off with no duration. Noted because the code path is taken and a future reader will wonder.
2026-09-05 · USE-3 · SET-8 sign-out dialog now stops a running timer before submitting, per this ticket out-of-scope note · The sign-out proceeds whether or not the stop succeeds: a failed stop costs a minute of record, and refusing to sign someone out over it would be far worse. This re-checks SET-8 AC 2 as the ticket asks.
2026-09-05 · USE-3 · *Add time by hand* and the session-row edit affordance · The ticket says to omit the first until USE-4, which is done. `SessionRow` REQUIRES `onEdit`, so the affordance is present with a no-op handler rather than absent — omitting it would have meant changing the component for a caller that is two tickets from wanting it.
2026-09-05 · USE-3 · **Not verified: acceptance criteria 1–14, including all five Vigil timer paths** · Every one needs a database, a browser, and in two cases a second device; no Supabase project is wired to this repository, so none of start-then-reload, start-on-A-open-B, the second timer, done-with-a-timer-running, or auto-close-with-a-timer-running has been induced. **That is the entire risk of this ticket and it is unproven.** What WAS verified: AC15 four commands; the store elapsed arithmetic across a fresh start, a resume with twelve minutes already logged, and a tick behind the start, which clamps to zero rather than going negative; and the late-start predicate across nine shapes, where a materialised fixed item reads `now` from its start through its end and becomes a late start only after it, a window only after it closes, and an unscheduled item never. The one-session-at-a-time rule, the idempotent start, and the auto-close interaction are readable but not run.

2026-09-05 · USE-8 · The unique key is a CONSTRAINT with `NULLS NOT DISTINCT`, not a unique index · The ticket says index; `nullsNotDistinct` is only available on the constraint form in Drizzle 0.45. The distinction is load-bearing rather than stylistic: Postgres treats NULLs as distinct by default, and every N6 row has a null `target_id`, so two Sunday reminders would both insert and both send. `ON CONFLICT` needs a constraint anyway, which is how the jobs use it.
2026-09-05 · USE-8 · `services/notification/` was merged into `services/notifications/` · SET-9 created the singular directory beside INF-9 plural one, which left two folders for one domain. INF-9 name came first, so it won; `build-payload.ts`, `deliver.ts` and `list-prefs.ts` all live there now.
2026-09-05 · USE-8 · N4 *Later* carries a `snoozeDate` in the payload rather than a delivery id, and the worker POSTs it · The ticket sketch has the worker sending `{ deliveryId }`; a browser has no business knowing a row id, and deriving the target from the day and the session on the server means a tampered payload can only ever snooze the poster own reminder. *Later* opens nothing at all — taking someone to the review after they said "not now" would be the opposite of what they asked.
2026-09-05 · USE-8 · `WebPushPayload` gained `actions`, `actionUrls` and `snoozeDate` · INF-9 payload carried only a title, body and url, so the action buttons §8.6 describes had nowhere to travel. An action with no `actionUrls` entry falls back to the body tap rather than swallowing it — a button that appears and then does nothing is worse than one that lands somewhere sensible.
2026-09-05 · USE-8 · Foreground suppression checks for a FOCUSED window, not merely an open one · Epic 2 §12 call 9 says a foregrounded push surfaces nothing. A backgrounded tab is not somebody watching, so an open-but-unfocused window still gets the notification — which is the case that matters, since the phone is usually locked with the tab still open.
2026-09-05 · USE-8 · Migration `0003_flaky_major_mapleleaf.sql` creates `notification_deliveries`, journalled at idx 3, NOT APPLIED · Per the standing instruction, the SQL is authored and a human applies it. `SCHEMA_REFERENCE.md` and the generator narrative were regenerated to name the table, its exactly-once key and its service-role-only policies — that bullet previously read "nothing uses it yet".
2026-09-05 · USE-8 · **Verified: acceptance criteria 11, 13 and 15. Not verified: 1–10, 12, 14 — every Vigil path** · AC11 payload register was read and checked: the only literal sentences in `build-payload.ts` are *Close out today* and *Next week isn not planned yet*, both §8.2 verbatim, plus the five action labels and the item pluralisation inside §8.2 own two counted phrases. 2026-09-06 · USE-4 · `removeOneOff` now returns the item WITH its sessions and any miss, not just the row · Both cascade from `day_items`, so the delete takes them and no later insert can bring them back. AC7 requires the undo to restore the item "with its sessions and notes", which a row-level restore cannot do — they are read before the delete and re-inserted by `restoreOneOff`. Notes live on the item row and travel with it.
2026-09-06 · USE-4 · `ItemDetailView` gained `habitArchived`, `templateNameSnapshot` and `dayCloseTime` · The ticket names the first two; the third is IT-02 field bounds, which must be the day own window and therefore its own close time. Reading a close time from the account instead would put the wrong bound on any day whose snapshot differs from the current setting.
2026-09-06 · USE-4 · Pause leaves `completion_state = active` and is DERIVED rather than stored · There is no paused column: the state is "time logged, no open session, still active", which only a pause produces — a stop returns the item to `upcoming`. A flag would be a second fact that could disagree with the sessions, which are the timer truth.
2026-09-06 · USE-4 · Two error strings are marked `[COPY — needs Vesper sign-off]` beyond the ticket own three: a session in the future and one outside the day window · The ticket anticipates the first; the second falls out of bounding the fields to the day, which it also asks for. 2026-09-06 · USE-4 · **Verified: acceptance criterion 10. Not verified: 1–9** · Every one needs a database and a browser, and no Supabase project is wired here. What WAS verified: the four commands; the overlap predicate rendered SQL, which brackets correctly and reads `tstzrange(started_at, COALESCE(ended_at, now())) && tstzrange($from, $to)` — the `COALESCE` is what makes a RUNNING session count, so a manual entry cannot double-count the stretch a timer is recording; and the range algebra across nine shapes, where identical, contained, straddling and enclosing all overlap while BACK-TO-BACK does not. **That last case is load-bearing: pause-then-resume produces two sessions that touch, and a predicate treating touching ranges as overlapping would make resume impossible.** Postgres half-open `[start, end)` gives the right answer.

2026-09-06 · USE-5 · The axis bounds cover every DRAWN minute, not only the blocks · A ghost at 07:45 for an item started at 14:52, and a shift band, both sit on the axis; bounding to the blocks alone would put them off the top of it. 2026-09-06 · USE-5 · **Verified: acceptance criteria 14 and 15. 2026-09-06 · USE-6 · **The write is `shift.commit`, not `shift.apply`** · tRPC reserves `apply` — a router is an object and `apply` is `Function.prototype.apply` — and rejects it when the router is constructed. The type-check does not see this; `yarn build` does, failing at page-data collection. `commit` reads correctly beside `preview` anyway: preview, then commit.
2026-09-06 · USE-6 · The fit arithmetic lives in `@syn/utils/day/shift-fit.ts`, pure, and the service only feeds it rows · The ticket's advisory recommends this and it is what makes the preview and the write provably the same computation. Probed against six cases: no overflow; a hard anchor; past the day's close; done/running/hard/unassigned all refusing to move; an already-passed hard item never cut; and a moved item ending exactly on an anchor's start counting as fitting.
2026-09-06 · USE-6 · **Overflow is independent per item under the stated rule, so the "recompute after each cut" loop terminates in one pass** · An item overflows against the HARD anchors and the day's end, never against another soft item — so cutting one can never resolve another's, and the suggested set is simply every overflowing item, sorted by `compareForTrim`. The ruling's recompute instruction is honoured by `overMinutes` being called with the live cut set on every change rather than by a loop; the function's header states that a soft-soft term would be what forces a real loop. Recorded because the ruling implies an interaction the rule does not have.
2026-09-06 · USE-6 · `passedHard` is read as "hard, undone, assigned items whose start is at or before now", not "items the shift moves into the past" · Hard items do not move, so a shift cannot push one into the past; the honest reading of §5.6's "a hard item made already-passed is flagged, not cut" is that the person is late and those appointments have gone by. The label *Already passed — will show as late* matches that reading.
2026-09-06 · USE-6 · The undo derives the moved set rather than storing it, exactly as the ticket's note recommends · `shifts` has no id list, so the reversal subtracts `delta_min` from the soft, undone, assigned, undeferred items on the day, excluding the ones it has just restored from `cut_by_shift`. An item finished in the meantime is excluded and KEEPS its moved time — it is a record now, and its `done_at` is real regardless of what its planned time says.
2026-09-06 · USE-6 · `isLateOffer` lives in `@syn/utils`, not in `@syn/api` · Both `shell.status` (at fetch time) and the status line (on the minute tick) need the same answer, and importing `@syn/api` into a client component to reach a five-line predicate would pull the whole API package — routers, services, `web-push` — into the browser bundle. It is pure day arithmetic and belongs with the rest of it.
2026-09-06 · USE-6 · `shell.status`'s `firstFixedStartToday` now filters `completion_state = upcoming` · SYS-1 selected the first fixed assigned item without it, so a first item already DONE would have been read as evidence of running late. The offer would have appeared to someone half an hour into a day that was going fine.
2026-09-06 · USE-6 · The late offer navigates to `?sheet=shift` rather than opening SF-01 itself · The status line is chrome above the page and has no `DayView` to hand the sheet; the page has one. The param is read once and stripped, the same way a notification landing is, so a shift sheet cannot reopen on every back.
2026-09-06 · USE-6 · SC-02's *Undo this shift* is ABSENT when ineligible, not disabled · A greyed *Undo* on a record that has settled invites a tap that can only fail, and settling is not an error state — it is the point. The server returns which of the three refusals applies (`expired`, `later_shift`, `done_anyway`) rather than a bare boolean, because they are not the same thing.
2026-09-06 · USE-6 · **Not verified: acceptance criteria 1–11, and all six Vigil paths** · They need a seeded day with hard and soft items, one done and one running, a second account, and a fixed clock; no Supabase project is wired to this repository (INF-6, SET-2, SET-3, SYS-1, SYS-3, SYS-5 logged the same gap). **What WAS proven, by running it:** the fit arithmetic against six cases (above), including that done, running, hard and unassigned items are all excluded from the moved set and that an already-passed hard item never enters the suggested cuts; that the tally is coherent — 150 min over, cutting a 30-min item frees 30 and leaves 120, cutting all leaves 0; that both write statements render as valid, fully parameterised SQL (`make_interval(mins => $n)` and `<> ALL(ARRAY[$n::uuid, …])`, with the ids as placeholders rather than interpolated); that `"shift"` is a real `miss_resolved_by` value; and AC 12's four commands. **What is unproven is the sheet, the writes, and the undo's three refusals — not the fit rule or the SQL's shape.**
